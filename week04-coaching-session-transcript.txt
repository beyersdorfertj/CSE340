One small nuance worth knowing, just to sharpen the picture: because the

your instinct to escape is completely correct — it's your defense against
precisely that break-out trick.

Let's dig into the "why a session" part, because that's the real insight.

When you call res.redirect(...), the browser makes a brand-new, separate
HTTP request to the new URL. And HTTP itself is stateless — the server
doesn't inherently remember anything between one request and the next.

Given that the redirect is a completely separate request, where does that

the two requests, and how does the server know it belongs to this specific
user?


STUDENT:
In flash.js you define a structure you use to the messages in the users

COACH:
(Reviewed src/middleware/flash.js together.)

Yes — you found it exactly. Your flash.js middleware attaches a req.flash
function that reads and writes req.session.flash, organized into success,
error, warning, and info arrays. When you set a message it's pushed into the
session, and when you retrieve it, it's returned and then cleared — which is
what makes it "flash": shown once, then gone. That's a really clean
implementation.

So the message lives in req.session.flash between the two requests. That's
half the answer. The other half: how does the server, on that second
request, know which user's session to look in?

When the browser makes that second request after the redirect, what does it
send along that lets the server match it back to this specific user's
session data?


STUDENT:
The session ID stored in a cookie


COACH:
Perfect — that's exactly it. The browser stores a session ID in a cookie
(with express-session, it's typically connect.sid), and it automatically
sends that cookie on every subsequent request. The server uses that ID to
look up the matching session on the server side, finds req.session.flash,
and pulls out the messages. The actual message text never lives in the
cookie — only the ID does. You've connected the whole chain: stateless HTTP
-> session stored server-side -> identified by a cookie -> flash message
survives the redirect. Excellent work.
