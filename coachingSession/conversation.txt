Let's move to Topic 2: JavaScript Language Principles.

STUDENT (Topic 2 — JavaScript Language Principles — code snippet):
const NODE_ENV = process.env.NODE_ENV?.toLowerCase() || 'production';

--------------------------------------------------------------------
COACH:
Nice choice — that single line is packed with JavaScript language
features: reading from process.env, the optional chaining operator ?.,
a method call, and the || operator all working together.

Can you walk me through what this line does step by step — and in
particular, why did you use the ?. before .toLowerCase() instead of just
writing process.env.NODE_ENV.toLowerCase()?

--------------------------------------------------------------------
STUDENT:
It defines something which will be unchangeable with the name NODE_ENV.
"process.env." tries to read an environment variable "NODE_ENV" (which
is different to the first one) and converts it to lower case if found.
If not, it returns undefined which is falsy and because of this it will
use 'production' instead. As .env sets this variable to "development" but
is ignored by Git, the outcome of this line is just that you can show or
use your environment setting.

--------------------------------------------------------------------
COACH:
Really strong breakdown, Jörg — you nailed the short-circuiting of || and
the falsy-undefined fallback, and the detail about .env being git-ignored
shows you understand why a default matters.

Let me zoom in on one subtle point. You said the ?. means it "returns
undefined if not found." That's true of process.env.NODE_ENV on its own —
but consider the .toLowerCase() call specifically:

If you had written process.env.NODE_ENV.toLowerCase() (without the ?.)
and the variable was not set, what exactly would happen at that point —
would you still get undefined, or something else?

--------------------------------------------------------------------
STUDENT:
process.env.NODE_ENV would deliver undefined, which is NOT a string. I'm
not sure if undefined has a function toLowerCase(), but I would expect to
get a specific error telling me that the type is not correct or so.

--------------------------------------------------------------------
COACH:
Exactly right — and your instinct about "the type is not correct" is spot
on. You'd get a TypeError: Cannot read properties of undefined (reading
'toLowerCase'). undefined has no .toLowerCase() method, so calling it
throws and crashes.

That's precisely what the ?. prevents: if the left side is undefined or
null, the whole chain short-circuits to undefined without ever attempting
the method call — and then your || 'production' catches that undefined and
supplies the default. So the two operators are a little team: ?. avoids
the crash, || provides the fallback. Topic 2 done.

COACH:
That's a textbook-perfect answer, Jörg — <%- outputs raw, unescaped HTML
(correct for injecting a trusted partial's markup), while <%= escapes the
value so characters like < become &lt;, defending against cross-site
scripting. You clearly understand why the distinction matters, not just
the syntax.

You noticed that title is used both in header.ejs and in the page itself,

    const title = 'Service Categories';

--------------------------------------------------------------------
STUDENT:
There is only one render function handling both the include and the title

--------------------------------------------------------------------
COACH:
Exactly — there's a single render pass, and the object you pass ({ title })

include('partials/header'), the partial is rendered in that same scope, so
it inherits access to title automatically. That's the elegant part: one
data object, available to the page and every partial it pulls in. Topic 3

This is interesting because it combines a CSS variable with the min()
function to handle responsive width and centering without a media query.

Exactly right — min() picks the smaller value, so the layout is capped at
